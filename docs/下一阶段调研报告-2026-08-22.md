# VerbTask 下一阶段工作调研报告

日期：2026-08-22  
审计基线：`main` / `835045d` / `0.4.11+1`

## 1. 调研结论

VerbTask 已经具备较完整的功能表面，但当前的主要问题不是“还缺少多少按钮”，而是“数据、提醒、同步和发布是否足够可信”。仓库中的测试数量已经达到 171 项，但其中一部分只证明 Flutter widget 能构建，不能证明真实 Android/Windows 行为；同时存在多处文档已经写成“完成”、代码或验收证据却没有闭环的情况。

当前基线验证：

- `flutter analyze --no-pub`：通过，`No issues found!`
- `flutter test`：171 项通过
- `flutter test`：存在多次 `tap()` 未命中警告，主要出现在测试点击“看板”标签的路径
- 调研开始时工作区：无未提交修改；本报告是本轮新增的调研文档
- 尚未证明：真实 Android 通知/后台/Doze、Windows Toast/托盘/安装升级、两台设备的 LAN 同步、有效 LLM 的可重复输出

因此下一阶段应以“先建立可信底座，再扩大体验和功能”为主线。

## 2. 最高优先级问题

这些问题在继续发布或声称“同步/提醒可靠”之前必须处理或明确降级产品承诺。

### P0-A：同步服务的认证边界不安全

证据：`lib/core/sync/http_transport.dart:8-26` 允许 `SyncServer` 使用空 token，空 token 时所有请求直接通过；服务绑定 `anyIPv4`。这意味着只要生产路径出现空 token，局域网内设备即可读取和写入任务。

下一步：生产构造禁止空 token；测试若需要无认证，使用显式的测试 transport 或明确的 `allowInsecureForTests`，不能让默认构造继续代表可运行服务。

验收：缺失、空值和错误 token 对 `/pull`、`/push` 均返回 401；正确 token 才能同步；响应不能泄露任务内容。

### P0-B：服务端推送没有统一执行任务级 LWW

证据：`lib/core/sync/http_transport.dart:46-57` 只按 `changeId` 去重，然后直接 `upsertTask`，没有比较现有任务的 `version/updatedAt/changeId`。这可能让旧任务覆盖新任务。

下一步：把 `ConflictResolver` 作为服务端和客户端共同使用的唯一比较入口，明确比较顺序和同值 tie-breaker；旧变更应被安全忽略或返回可诊断结果。

验收：服务端已有较新任务时，较旧 `version` 即使带新 `changeId` 也不能覆盖；较新版本可以覆盖；两端最终收敛。

### P0-C：损坏数据可能静默变成空仓库

证据：`lib/core/storage/file_repository.dart:20-43` 捕获加载异常后把任务、清单和变更列表置空。之后任何写入都有覆盖原数据的风险。

下一步：保留原文件并隔离为损坏快照，显示可恢复错误；在用户确认前禁止把空状态持久化。补 schema 版本读取和迁移入口。

验收：损坏 JSON、字段缺失、未来版本和临时文件场景都不丢原文件；用户可从备份恢复；迁移可重复执行。

### P0-D：通知点击 payload 与任务查询 ID 不一致

证据：`lib/core/notifications/reminder_service.dart:49-53` 将 `task.id-timestamp` 同时作为通知 ID 和 payload；`lib/main.dart:43-49` 把 payload 直接交给 `openTaskById`，而 `lib/app/open_task.dart:8-22` 只按纯 `task.id` 查询。

下一步：通知数值 ID、任务 payload、重复实例标识分开建模。最小修复是 payload 只保存任务 ID；重复实例设计完成后再扩展为结构化 payload。

验收：前台点击、后台点击、冷启动点击都能打开对应任务；任务已删除时显示可理解结果而不是静默失败。

### P0-E：发布产物不可信

证据：`pubspec.yaml:4` 为 `0.4.11+1`，但 `installer/verb_task.iss:4` 仍为 `0.4.10`；`android/app/build.gradle.kts:25-28` 使用 debug signing；仓库没有 GitHub Actions，也没有版本 tag。

下一步：先暂停宣称“可发布”，建立单一版本源、release signing 方案、构建产物检查和 CI。密钥不能提交仓库，正式签名需由发布环境注入。

验收：APK 通过 `apksigner verify` 且不是 debug 签名；安装器、EXE、APK、tag、Release 说明版本一致；干净环境安装启动成功。

## 3. NLP/LLM：当前用户最直接遇到的问题

### 已确认缺口

`lib/core/nlp/nlp_service.dart:48-78` 在 LLM 返回非空标题后直接采用 LLM 字段。LLM 如果把 `rrule` 或 `reminderMinutes` 返回为 `null`，当前代码不会再合并本地解析结果。现有安全网只能在 LLM 已返回 `rrule` 时补 `BYDAY/BYHOUR` 等局部内容。

最小复现：

```text
每隔2天提前30分钟浇花
```

如果 LLM 返回只有标题的 JSON，最终结果会同时丢失重复和提醒；而本地解析本来可以识别其中至少一部分。

本地规则还缺少或容易误判：

- 提醒同义词：`通知我`、`提示我`、`到点叫我`、`别忘了`、`记一下`
- 提醒否定：`不用提醒我`、`无需提醒`、`不要提醒`
- 重复口语：`每两周`、`两周一次`、`每隔两周`、`隔天`、`隔周`、`每个周末`
- LLM 结果和本地显式语义冲突时的优先级

### 建议的下一步

1. 先写字段级合并的失败测试：本地检测到明确提醒/重复时，LLM 缺字段不能丢失；明确否定时不能被关键词安全网误判。
2. 定义字段优先级：提醒和重复中的明确词法结果优先；LLM 可补充本地无法识别的复杂规则；标题、日期和优先级继续由 LLM 主导但必须经过安全校验。
3. 扩大本地中文规则并为每种表达添加参数化测试。
4. 修改 `tool/llm_mass_probe.dart`，真正读取 `docs/nlp_llm_cases.json` 的 `expect` 并返回非零失败码。
5. 真实接口测试与默认 CI 分开：CI 使用固定响应或本地 OpenAI-compatible fake server；真实接口测试手动执行，记录日期、时区、base URL 和模型，不把 key 写入日志。
6. 评估将 LLM key 从明文 `settings.json` 迁移到 Android Keystore / Windows Credential Manager；至少先确认备份和日志绝不包含 key。

### NLP 验收门槛

- 结构化字段不得因 LLM 缺省而静默消失
- 明确“不提醒”必须优先于提醒关键词
- 现有 JSON case 全部有自动断言，不再依赖人工看输出
- 本地解析、LLM 解析、LLM 失败回退三条路径分别有测试
- 确认弹窗展示最终合并结果，用户能在提交前修改

## 4. 提醒与重复任务可靠性

### 当前风险

- `lib/core/notifications/reminder_service.dart:32-41` 把“提醒列表为空”同时解释为“继承全局默认”和“用户明确关闭”，单任务关闭可能无法覆盖全局默认。
- `lib/core/notifications/reminder_service.dart:43-50` 每个重复任务只计算一个下次实例；`RRuleService.instancesBetween` 尚未用于通知预排。
- 编辑页保存任务后没有明确统一触发重排；旧通知可能残留。
- 日期-only 值、UTC 展开、本地时区和 DST 的语义没有形成模型契约。
- `lib/core/notifications/platform_notification_sink.dart:111-112,125-129` 根据精确闹钟能力在 `exactAllowWhileIdle` 与 `inexactAllowWhileIdle` 之间选择；Manifest 的 `SCHEDULE_EXACT_ALARM` 与该动态策略一致。仍需在 UI 说明无精确权限时可能出现延迟并展示当前状态。
- 重复任务的数据模型没有实例例外，无法实现需求中“只改这一次 / 这一次及以后 / 整个系列”。

### 建议拆分

先做不需要大规模模型迁移的修复：通知 payload、编辑/完成/删除后的统一重排、全局默认与单任务关闭的测试和权限状态反馈。

之后单独设计重复实例模型：`occurrenceKey`、实例例外、单次完成/跳过和系列编辑策略。这个工作不能只靠在编辑页增加几个按钮，否则同步、通知和回收站都会产生不一致。

### 验收矩阵

- 全局默认开启 + 单任务明确关闭：不产生通知
- 单任务显式提醒：覆盖全局默认
- 修改截止时间/提醒/RRULE：旧通知取消，新通知出现
- 完成、删除、恢复、导入：通知状态一致
- `COUNT`、`UNTIL`、月末和无效 RRULE：不崩溃且停止条件正确
- Android 13+ 权限拒绝、重新授权、系统设置关闭：界面有可恢复入口
- force-stop、重启、Doze、无网络和恢复网络后：提醒与数据状态可解释

## 5. 局域网同步与数据层

### 当前缺口

1. `/pull` 始终拉完整快照，cursor 没有被客户端使用；`SyncClient.runSync` 传入空 `seenChangeIds`。
2. 自动同步设置保存了分钟数，但 `background_sync.dart:40-49` 注册周期固定为 30 分钟。
3. Android 没有明确的回前台自动同步接线。
4. Windows `SyncHost` 启动错误被吞掉，用户看不到端口冲突、防火墙或服务失败原因。
5. 清单删除没有墓碑；物理删除可能在另一端重新出现。
6. 永久删除没有同步 tombstone，而全量快照可能让任务复活；产品必须明确这一行为。
7. JSON 导入逐条写入，不是原子操作；中途坏记录会留下部分导入。
8. 没有 schema migration，后续增加 cursor、墓碑或提醒策略会影响旧文件。
9. LAN 是明文 HTTP Bearer token，没有轮换/撤销策略。
10. 同步 UI 没有 loading、最近同步时间、设备数、失败原因和重试入口。

### 建议顺序

1. 先修空 token、服务端 LWW、损坏文件保护。
2. 再实现 cursor、change 去重和成功提交规则；同步中断时不能丢变更。
3. 增加列表墓碑、永久删除语义和数据迁移。
4. 把设置的同步间隔接入实际 WorkManager 注册，并在前台恢复时触发一次。
5. 加同步状态 UI，再考虑二维码配对、设备列表和 token 轮换。

### 同步验收矩阵

缺失/错误 token、双向新增、后改覆盖先改、重复 push/pull、断网重试、清单删除、回收站删除/恢复、永久删除、时钟偏差、导入中断和旧版本迁移都必须有确定结果。至少要有两端真实 LAN 冒烟，不能只靠同进程 mock。

## 6. Android/手机端体验

### P2 工作

- 精确闹钟权限声明与当前动态调度策略一致：能力可用时使用 `exactAllowWhileIdle`，不可用时使用 `inexactAllowWhileIdle`；待补充 UI 状态和降级延迟说明。
- 修复测试中的 hit-test warning，再把这类 warning 设为失败。
- 增加系统字号 1.3/1.5/2.0、键盘弹出、横竖屏和窄屏截图对比。

### 手机验收门槛

使用 API 35/36 模拟器或真实 Android 设备，至少覆盖 320/360dp、系统字号 1.0/1.3/2.0、浅色/深色、中英、输入法、通知权限、force-stop、Doze 和重启。每个关键流程保存截图和 logcat，不再把大尺寸 widget 测试当成手机验收。

## 8. 推荐执行路线

### 阶段 0：建立事实和门禁

不改业务行为，先把测试 warning、版本来源、case runner 和验收清单变成可重复门禁。这样后续每次修复都能知道是实际变好还是只增加了文档。

### 阶段 1：v0.4.12 信任修复

建议集中处理：LLM 字段级合并、提醒否定、通知 payload、任务变更后的重排、空 token、服务端 LWW、损坏数据保护、Windows 安装器版本和 Android release 配置。每项先写失败测试，再实现。

### 阶段 2：手机端真实可用

处理窄屏/大字号/触控热区、通知权限反馈、后台失败重试和同步间隔生效；在模拟器和真实设备执行可复现的截图、adb 和 logcat 验收。

### 阶段 3：同步可靠性 v0.5

实现 cursor/change 去重、列表墓碑、迁移、原子导入、失败恢复和同步状态 UI；完成两端 LAN 冲突、删除和断网测试后再考虑扫码配对。

### 阶段 4：重复任务完整语义

设计并实现重复实例、系列编辑、单次完成/跳过、时区/DST 和多实例通知预排。这是一次数据模型升级，应单独写设计文档和迁移计划。

### 阶段 5：Windows 正式发布

统一品牌和图标，完成托盘/自启/速记/DPI/Toast/安装升级验收，建立 CI 和 Release 流程，最后才发布新的安装包和 APK。

## 9. 暂时不要做的事情

- 不要先继续堆 LLM prompt，而不做字段级合并和自动断言。
- 不要先做二维码配对；当前手动 token、鉴权和 LWW 仍未形成可靠底座。
- 不要现在引入 SQLite、CRDT 或完整云同步；它们会扩大范围，且不是当前用户痛点。
- 不要用一次大尺寸 widget 测试或“安装器能编译”替代真实 Android/Windows 验收。
- 不要在未确认重复实例数据模型前，为“只改这一次”临时添加 UI 开关。

## 10. 调研限制

本报告基于当前仓库代码、测试、设计文档、静态审计和本地 `flutter analyze`/`flutter test`。本轮没有修改产品代码，也没有把有效 LLM key 写入日志；真实 Android、Windows 和双设备 LAN 场景仍需按上述验收矩阵实测。因此本报告是下一阶段执行依据，不是“所有功能已验收”的结论。
